# AGENTS.md

Инструкции для ИИ-агентов, работающих в этом репозитории.

## Приоритеты

1. Корректность и отсутствие регрессий.
2. Простой, производительный и поддерживаемый код.
3. Минимальный расход токенов и короткая коммуникация.
4. Доступная семантическая HTML-разметка и современные SCSS-стили.
5. Актуальная документация архитектуры в `docs/diagrams/`.

Экономия токенов не оправдывает непроверенные изменения, минификацию исходников или потерю важного контекста.

## Работа с контекстом и ответы

- Сначала изучай только файлы, относящиеся к задаче. Для поиска используй `rg` и `rg --files`.
- Не читай целиком большие каталоги, сгенерированные файлы, `dist/`, `node_modules/` и lock-файлы без необходимости.
- Не повторяй содержимое файлов и длинные логи в чате. Показывай только вывод, необходимый для решения или проверки.
- Объединяй независимые чтения и проверки. Не дроби простую работу на лишние шаги и сообщения.
- Статусы давай только перед работой, при существенном этапе, длительном ожидании или блокировке.
- Финальный ответ делай кратким: результат, изменённые файлы, выполненные проверки и реальные ограничения.
- Большие отчёты и схемы сохраняй в файлы; в чате давай ссылку и краткое резюме.
- Не удаляй полезные комментарии и не минифицируй исходный код ради экономии токенов.

## Границы изменений

- Сохраняй текущую архитектуру и стиль затронутого проекта, если задача не требует их изменения.
- Не редактируй несвязанные файлы и не перезаписывай пользовательские изменения.
- Общую повторно используемую логику размещай в `utils/`; логику отдельного эксперимента оставляй внутри него.
- Новые эксперименты создавай через `npm run create:experiment -- <name> --brand <brand> --style scss`.
- Не добавляй локальные `package.json`, `node_modules` или `vite.config.*` в папки экспериментов.
- Используй alias `@utils` для корневых утилит.
- Не редактируй вручную содержимое `html-build/` и `dist/`, если задача явно не относится к готовому артефакту.

## JavaScript

- Используй современный ESM и возможности JavaScript, поддерживаемые текущей сборкой Vite.
- Предпочитай небольшие функции с одной ответственностью, ранние возвраты и понятные имена.
- Не создавай абстракции без повторного использования или явного упрощения кода.
- Минимизируй обращения к DOM: кешируй повторно используемые элементы, группируй изменения и избегай принудительных перерасчётов layout.
- Для частых событий применяй `debounce`, `throttle` или `requestAnimationFrame`, когда это действительно нужно.
- Удаляй обработчики, observers, timers и другие ресурсы при завершении жизненного цикла.
- Проверяй наличие DOM-узлов и внешних API. Повторная инициализация виджета должна быть безопасной.
- Не используй глобальное состояние, `innerHTML` с недоверенными данными и бессрочные наблюдатели без необходимости.
- Не дублируй имеющиеся функции из `utils/`; сначала проверь доступный API.
- Комментарии должны объяснять причину или ограничение, а не пересказывать код.

## SCSS

- Для новых экспериментов предпочитай `.scss`. Не переписывай существующий CSS в SCSS без причины.
- Изолируй стили уникальным корневым классом или префиксом конкретного виджета.
- Используй вложенность умеренно, не глубже трёх уровней; избегай чрезмерной специфичности и `!important`.
- Применяй CSS custom properties для повторяемых значений, темизации и runtime-настроек; SCSS-переменные — для compile-time вычислений.
- Используй современные возможности CSS: flex/grid, `clamp()`, логические свойства, медиавыражения по содержанию.
- Сначала обеспечь адаптивную базу, затем добавляй breakpoint только там, где ломается композиция.
- Учитывай `prefers-reduced-motion`, состояния `:focus-visible`, hover и disabled.
- Анимации делай через `transform` и `opacity`, если нет обоснованной причины менять layout-свойства.

## HTML

- Используй семантические элементы по назначению: `button` для действий, `a` для переходов, заголовки в логической иерархии.
- Интерактивные элементы должны работать с клавиатуры и иметь доступное имя.
- Для изображений указывай осмысленный `alt`, размеры при возможности и пустой `alt` для декоративных изображений.
- Связывай `label` с полями формы; корректно используй `name`, `type`, `autocomplete` и сообщения об ошибках.
- ARIA добавляй только когда нативной семантики недостаточно. Не имитируй кнопки с помощью `div` или `span`.
- Не используй повторяющиеся `id`. Боевые идентификаторы и классы должны иметь уникальный префикс виджета.
- Не вставляй недоверенные данные через HTML-строки. Для пользовательского текста используй безопасные DOM API.

## Проверка

- Выполняй минимальный релевантный набор проверок, затем расширяй его пропорционально риску.
- Для общих JS-изменений используй: `npm test`, `npm run lint`, `npm run typecheck`.
- Для конфигурации экспериментов дополнительно используй `npm run validate:configs`.
- Для конкретного эксперимента проверяй его сборкой: `npm run build:experiment -- <path>`.
- Не исправляй посторонние ошибки, но явно сообщай о них, если они мешают проверке задачи.

## Граф-схемы проекта

- Все исходники схем храни в `docs/diagrams/` в формате Mermaid (`.mmd`).
- При изменении архитектуры, зависимостей, процесса сборки или жизненного цикла обновляй соответствующую схему.
- Одна схема должна раскрывать одну тему; крупные схемы разделяй на несколько файлов.
- Названия файлов используй в `kebab-case`, например `project-architecture.mmd`.
- В `docs/diagrams/README.md` поддерживай индекс схем и кратко указывай назначение каждой.
- Не добавляй сгенерированные PNG/SVG, если они явно не нужны задаче: Mermaid-файл является источником истины.
